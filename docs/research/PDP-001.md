## Abstract

We investigate **proof-carrying task decomposition**: transforming a formally specified task into smaller, independently executable subtasks, with explicit boundary obligations that permit a verifier to establish that their composition satisfies the original task contract. The inspiration from Hamilton–Perelman Ricci flow and surgery is structural: distinguish gradual improvement from controlled cutting, recognize candidate bottlenecks, require invariants before and after transformation, and preserve a global proof through local modifications. The proposal does **not** assert that Perelman's geometrical theorems imply universal computable decomposition, that graph Ricci curvature proves software modularity, or that arbitrary tasks are decidable.

An implementation combines Lean 4 certificates, a deterministic Python orchestrator, a three-valued epistemic status, scoped agent capabilities, content-addressed provenance, and an optional graph-based Ricci-inspired cut heuristic. The first scientific target is a **conditional composition theorem**, not a claim that every difficult problem is easy when split. The first product target is a minimal "Upwork for Robots" platform whose completion claims are backed by independently verifiable receipts.

## 1. Motivation and scope

**Problem:** Today agent schedulers can parallelize tasks but commonly lack a formally checked statement connecting successful subtasks to the user's actual goal. They may claim success without tool execution, accept stale evidence, omit an interface requirement, or leak scope across agents. Conventional divide-and-conquer alone does not address these errors.

**Hypothesis H-PDP:** For useful, precisely stated classes of tasks, typed surgery operators and explicit gluing obligations enable recursive decomposition with sound, auditable recomposition; in some task families this reduces wall-clock time or increases robustness relative to a monolithic baseline, after accounting for verification and coordination.

**Excluded claims:** universal completeness, a general solution to computationally undecidable problems, P=NP, a proof of metaphysical reality, an exact identification of a task space with a smooth Riemannian manifold, or guaranteed speedup.

**Research questions:**
- RQ1: What minimal boundary contract is sufficient for sound recomposition?
- RQ2: Under which well-founded measures is the recursion terminating?
- RQ3: Which partitioners (syntactic, dependency-graph, cut-based, curvature-inspired) produce better verified outcomes at bounded cost?
- RQ4: How can a task receipt distinguish theorem, machine result, testimony, inference, opinion, and absence of evidence?
- RQ5: Can untrusted worker agents participate without inheriting authority to approve their own work or write protected branches?
- RQ6: Can the workflow produce both rigorous mathematical publications and usable software packages?

## 2. Precedents and the precise analogy

Hamilton introduced the Ricci flow for metrics; Perelman's entropy and no-local-collapsing analysis, followed by controlled Ricci-flow surgery in three dimensions, supply a compelling pattern of evolving a global object while treating singular structure rigorously. This is methodological inspiration, not a reduction theorem from topology to programming.

**Translation table:**
- Geometric state -> typed task state and dependency graph.
- Flow -> semantics-preserving local simplification or progress step.
- High-curvature neck / bottleneck -> candidate interface with high coupling or obstruction.
- Surgery -> decomposition plus obligations and reconstruction rule.
- Preserved topology / controlled geometry -> preserved task semantics, security and specified invariants.
- Global geometrical conclusion -> independently checked recomposition certificate.

Discrete Ollivier–Ricci curvature and network Ricci flow are established methods to *suggest* graph community boundaries; they are not proof of logical soundness. We therefore place topology-inspired heuristics outside the trusted proof core.

Relevant work: Perelman (2002, arXiv:math/0211159), Perelman (2003, arXiv:math/0303109), Ni et al. (2019, arXiv:1907.03993), Necula (1997, Proof-Carrying Code), assume–guarantee reasoning, interactive theorem proving, build provenance and content-addressed storage.

## 3. Formal objects and semantics

A task is a typed contract, not an unconstrained natural-language prompt:

    Task := (id, Inputs, Preconditions, Goal, Invariants,
             AllowedActions, CapabilityScope, EvidenceSchema,
             DataPolicy, ResourceBudget, Environment, Version)

A witness is evidence of a claimed result under the stated assumptions. A verifier is a separately defined deterministic predicate on the task, witness, and available trusted context:

    Verify(T, w) : Result[Accepted | Rejected | Unresolved]

For formal theorem tasks, Accepted requires a kernel-checkable proof under an explicitly enumerated assumption set. For software tasks, Accepted means the specified test/contract evidence passed, **not** universal program correctness. For external-world claims, there may be no complete decidable verifier; record the narrower observation and use Unresolved for unjustified universal conclusions.

**Epistemic status** is distinct from dispatch policy:
- TRUE: proof or explicitly bounded acceptance certificate for the exact claim.
- FALSE: verified refutation or counterexample for the exact claim.
- UNKNOWN: neither has been sufficiently established.

An intentionally small decision router chooses EXECUTE, SURGERY, ESCALATE, or STOP based on status, available operators and policy; this is a control protocol, not itself a fourth truth value. If evidence conflicts, the minimal three-valued prototype returns UNKNOWN plus conflict metadata; a future extension may formalize four-valued evidence logic.

The authorized capability set **never** increases merely because a task is decomposed. Every subtask inherits a subset of the parent's permitted capabilities, or separately obtains a scoped authorization from a trusted issuer.

## 4. Surgery contracts and main theorem candidates

Define a surgery certificate as:

    S(T) = (T1, ..., Tn, Interfaces, Assembly, Obligations, Certificate)

A sound surgery specification must be paired with a theorem stating that every accepted child witness and every satisfied interface obligation induces a valid witness for T. The definition of Verify(T, w) must be independent of S; we must not bake global correctness into the definition of "valid surgery" and call the result a discovery.

**T1 — Conditional sound composition.** For a particular typed task domain D:

    [∀ i, Verify(Ti, wi) = Accepted]
    ∧ [CheckInterfaces(Interfaces, wi) = Accepted]
    ∧ [CheckSurgery(Certificate, T, {Ti}, Assembly) = Accepted]
    => Verify(T, Assembly({wi})) = Accepted.

Proof obligation: implement an independent semantic meaning of each contract and prove the reconstruction relation in Lean. The theorem must be explicit about ambient assumptions, trusted primitives, the possibility of inconsistent premises, and the scope of the verified claim.

**T2 — Finite termination.** Equip all tasks with a well-founded rank or relation, for instance rank : Task -> Nat. Require rank(Ti) < rank(T) for each child and a finite child set, with terminating leaf processors. Under these premises there is no infinite path in the decomposition tree. This does **not** bound total tree size usefully without branching bounds, nor ensure agents terminate unless the leaf executors do.

**T3 — Invariant preservation.** For each invariant I, a proof shows it is preserved by local flow transformations and by surgery/reassembly. Security labels, input constraints, provenance continuity and goal semantics must be individually formulated; "all invariants survive" is not an automatic theorem.

**T4 — Capability non-amplification.** Child capability sets are subsets of a parent's authorized scope (or require a separate, logged trusted grant). The orchestrator cannot silently delegate repository write credentials, private data or destructive actions.

**T5 — Provenance closure.** All material dependencies, exact object IDs, verifier code versions and outputs used in a claimed result are reachable from its receipt DAG. A source mutation invalidates dependent receipts until reverified. A cryptographic hash establishes integrity and identity, not independent truth or completeness.

**T6 — Counterexample safety.** If a purportedly sufficient interface omits a necessary condition, construct an explicit finite countermodel that passes child checks but fails the parent. The pilot must *reject* that surgery policy.

## 5. Operational algorithm

1. Parse user intent into a typed goal, constraints and explicit unknowns.
2. Canonicalize task data with versioned domain separation and length framing. Keep human language separate from canonical semantics.
3. Build dependency graph or hypergraph: claims, resources, prerequisites, shared state, effects and proof obligations.
4. Validate security and permissions before any execution.
5. Try low-cost local FLOW transformations (e.g., normalization, simplification, dependency elimination); record before/after semantic obligations.
6. If progress stalls, propose candidate SURGERY cuts using dependency separators, minimal-cut baselines or optional discrete curvature.
7. Reject cuts without a valid gluing schema and an admissible well-founded progress argument.
8. Dispatch leaf tasks to least-privilege workers, using sandboxed execution and resource budgets.
9. Collect content-addressed evidence receipts and verify independently. Treat missing receipts as UNKNOWN, never DONE.
10. Assemble only after child results, boundary obligations, and provenance DAG pass their designated validators; otherwise return unresolved subgoals and a counterexample or blocker.

A cut is evaluated with both logical admissibility and operational cost:

    NetGain = Cost(monolith) -
              [Sum(Cost(children)) + Cost(boundaries) +
               Cost(verification) + Cost(coordination)].

Separate *well-founded proof rank* from heuristic estimates of wall-clock time, tokens, energy, memory or money. Optimizing the second must not invalidate the first.

## 6. Candidate geometries: hypotheses, not axioms

Start with a directed, typed dependency hypergraph H=(V,E), where nodes are claims/actions and hyperedges represent multi-party assumptions or joint obligations. Define a derived metric only for the partitioning layer. Compare:
- BASE-0: no split (monolith).
- BASE-1: uniform file / syntax / AST module split.
- BASE-2: topological dependency separators or weighted min-cut.
- EXP-1: Ollivier–Ricci inspired edge weighting and discrete-flow-based community cuts.
- EXP-2: learned semantic embeddings as *candidate discovery only*.

Define a "bottleneck" quantitatively (cross-partition contract count, dataflow overlap, verification coupling), then measure whether curvature helps predict low-interface-cost cut surfaces. Negative curvature alone neither entails a valid surgery nor certifies a theorem.

No smooth manifold claim is required for the first release. A graph/poset representation with explicitly typed boundaries is the more conservative and experimentally falsifiable foundation.

## 7. Proposed architecture and trusted computing base

**Proof kernel:** Lean 4, isolated formal-methods package, explicit axioms with #print axioms, checkable theorem artifacts, no sorry/admit/unsafe proof bypass in acceptance path.

**Orchestrator:** Python 3.11+ package with deterministic triage, recursion, planner plug-ins, task DAG serialization, limits, agent adapter interfaces and receipts.

**Untrusted workers:** external models, human contributors, local machines, third-party services. Workers cannot mark themselves as VERIFIED or bypass parent policy. Execution permissions are allowlisted, scoped and revocable.

**Evidence ledger:** append-only or immutable-per-version receipt objects; authenticated tool event, input/output hashes, source refs, worker identity, trust level, timestamps, environment ID, version pin, dependency edges, budget and verifier result. A structured statement "tool was not called" is distinct from "tool was called and returned no matches".

**Merge gate:** separate from worker execution. Verify exact PR head SHA; require an up-to-date integration build, policy checks, license and secrets review, independent tests, and authoritative repository-side status. Optional automatic merge is restricted to preapproved risk classes. Public releases, branch-protection changes and destructive operations require explicit trusted authorization. Never accept prompt text as proof of GitHub write.

**Integration:** use existing Emergent Attractor Lean materials as an initial theorem-analysis fixture, and SSO's canonical scientific-object/hash-rarity pilot as an evidence-serialization and adversarial-data fixture. Neither package's currently unverified claims become axioms of PDP.

## 8. Reference data model (draft)

    kind: PDP-TASK/1
    id: sha256_of_canonical_task
    parent_id: optional
    inputs: [content-addressed references]
    preconditions: [typed claims]
    goal: typed claim
    invariants: [proof obligations]
    capability_scope: [read-only paths, explicitly granted tools]
    data_policy: PRIVATE
    resource_budget: {cpu_seconds: 600, tokens: 20000}
    status: UNKNOWN
    route: SURGERY
    surgery:
      children: [task IDs]
      interfaces: [typed boundary contracts]
      assembly: identified reconstruction function
      proof_certificate: exact artifact ID
    receipts:
      - subject: exact task ID
        code_rev: exact commit SHA
        input_digest: exact digest
        tool_receipt: actual tool provenance or ABSENT
        verifier: name, version, output digest
        result: ACCEPTED | REJECTED | UNRESOLVED

Serializations must distinguish absent, null and empty; reject ambiguous fields, unknown critical versions, noncanonical encodings and unauthorized references. Hashes are identifiers and tamper-evidence only.

## 9. Experiments and falsification

**E1 — Lean theorem disassembly.** Select a bridge theorem from the Emergent Attractor package. Split into assumptions, local lemmas and a compositional bridge. Independent workers attempt lemma proofs; a separate Lean build verifies both children and reconstruction. Compare with the unmodified monolithic proof. No empirical result is called VERIFIED before a fresh independent kernel replay.

**E2 — Program module decomposition.** Choose a small, deterministic Python package with nontrivial interfaces and measurable tests. Partition using BASE-0, BASE-1, BASE-2 and EXP-1, with equal model/tool budgets. Run blinded repetitions and record elapsed time, total model tokens, compute, failures, interface repair rounds and successful final tests.

**E3 — Red-team gluing.** Deliberately omit a cross-module invariant and provide child witnesses that pass locally but violate the global specification. A sound parent gate must reject the composed result.

**E4 — Evidence poisoning.** Submit forged DONE reports without tools, stale evidence from an old head SHA, wrong source object, high-similarity but changed semantics, modified receipts and missing provenance edges. Test exact-object resolution and fail-closed verification.

**E5 — Security.** Attempt read/write scope escalation via a child prompt, dependency metadata, a malicious PR title, log content and a worker-produced certificate. Authorization must come from typed trusted policy, not worker prose.

**E6 — Partition stress.** Construct indivisible or strongly coupled tasks; show that a bad cut can increase total work or have no admissible gluing contract. The planner must be able to refuse surgery.

For generated finite instances include seeds, generators, oracle solutions, exact commit IDs and machine-readable run receipts. Pre-register thresholds and report failures, not only successful cases.

## 10. Acceptance criteria

**Mathematical milestone:**
- Lean-checked typed task, surgery, interface and reconstruction model.
- Nontrivial instantiation of T1, T2 and T3.
- At least one concrete countermodel for an insufficient gluing condition.
- No unexplained axioms or sorry in certified modules; explicit audited assumptions.

**Engineering milestone:**
- Reproducible clean builds with lockfiles/toolchains.
- At least 20 deterministic positive and 20 adversarial negative instances across the test families.
- Zero falsely accepted results among the pre-registered deliberately invalid cases (a finite experimental criterion, not a universal guarantee).
- Every positive result includes the exact parent/children contract hash, verifier receipt and replay instructions.
- Strict separation of CLAIMED, CHECKED, PUBLISHED and MERGED states.

**Economic/operational milestone:**
- Report median wall-clock and total compute/token cost relative to all baselines, including verification cost and confidence intervals.
- Treat any proposed 20% wall-clock advantage as a falsifiable target, not as a presupposed conclusion.
- Explicitly document tasks for which partitioning loses or is rejected.

## 13. Smart merge governance

Smart merge means *proof-aware acceptance*, not trusting the self-assessment of an autonomous contributor.

Risk 0: documentation-only, no secret/privilege release impact -> scoped automated checks, then optional auto-merge if policy allows.
Risk 1: tests, bounded pure functions, examples -> CI + independent deterministic test review.
Risk 2: kernel, axioms, verifier, serialization, dependency lockfiles, protected workflows or security policy -> two independent reviews, fresh trusted build, no default auto-merge.
Risk 3: visibility change, external release, credential handling, economics/settlement or policy change -> explicit owner approval/veto mechanism; no unattended merge.

Protect main, require trusted check producers and immutable source SHA receipts. Use GitHub branch protection or rulesets and optionally a merge queue when supported and configured. The presence of "auto-merge enabled" alone does not prove the required rules exist.

## 15. Principal risks and publication rules

- **False global proof:** local certificates not sufficient without a trusted gluing theorem.
- **Incomplete three-valued semantics:** conflict may require richer evidence logic; never call it FALSE by default.
- **Misleading topological analogy:** formal test domains are graphs/contracts, not necessarily smooth manifolds.
- **Cyclic or exploding decomposition:** well-founded descent along branches need not ensure efficiency.
- **Resource abuse and secrecy leaks:** workers never receive implicit delegated authority.
- **Stale or spoofed evidence:** provenance invalidation is mandatory, and a hash never certifies truth.
- **License and attribution:** import provenance and adaptation notices must be preserved on every public artifact.
- **Overclaiming ontology:** Lean proves formulas relative to definitions and explicit premises, not physical/metaphysical existence.
